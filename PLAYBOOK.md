# Adding a dashboard — the playbook

This is the checklist a coding agent (or you) follows to add dashboard N to a Life OS
instance. Every step is demonstrated by the reference implementation in
`example/casework/`; when in doubt, mirror it. A "dashboard" = one life domain: a desktop
SQLite engine + a generated HTML page, surfaced on all three surfaces over the protocol in
`PROTOCOL.md`. Work the steps in order; each is independently verifiable.

Throughout, examples use the reference domain (a modern consulting detective's casework).
When your agent writes YOUR dashboard, your real data stays in your SQLite files — never
put real personal data in code, comments, seeds, or docs.

## 1. The engine  (`<your-dir>/<name>.py`)
- One folder per dashboard; the engine resolves its `.db` and `dashboard.html` relative to
  its own file, so the folder is relocatable as a bundle.
- Stdlib-only argparse CLI. An idempotent `ensure_db()` (CREATE IF NOT EXISTS + ALTER-guard
  migration list) runs on every invocation, so schema evolves without manual migrations.
- **Sync columns on every phone-editable table from day one**: `updated_at`, `updated_by`
  (default `'desktop'`), `deleted_at` (tombstone), `server_seq`. Plus the three support
  tables (`sync_counter`, `applied_mutations`, `conflict_log`) and the `_next_seq` /
  `_backfill_sync_seq` helpers — copy them from `casework.py`; they are domain-free.
  Backfill matters: a row whose `server_seq` is NULL is invisible to phone pulls forever.
- Deletes on syncable tables set `deleted_at`; every read filters `deleted_at IS NULL`.
- Export `SYNC_TABLES` (per-table op → engine-function config; id-keyed vs name-keyed) and
  `DESKTOP_ACTIONS` (browser-control actions). Include the `sync-status` and
  `resolve-conflict` subcommands so an assistant can run the conflict procedure.
- Every write stamps the sync columns and ends by regenerating the dashboard HTML.

## 2. Register with the server
- Add one line to `server/dashboards.config.json`. The server mounts the folder's statics
  at `/<name>/`, wires `/api/<name>/pull|push` from `SYNC_TABLES`, and
  `/api/<name>/desktop/<action>` from `DESKTOP_ACTIONS`.
- The push path enforces an exists-guard: non-create ops on rows that don't exist are
  rejected, because name-keyed engine functions typically upsert and a stale client name
  would silently create junk rows. Don't weaken it.
- Restart the server after engine/server edits, and run the engine's `dashboard` command
  once — static pages only regenerate on a write.

## 3. The dashboard page
- Generated by the engine (see `casework.py`'s builder): self-contained dark HTML, small
  vanilla-JS controls posting to the desktop endpoints, `location.reload()` on success,
  inline error and no reload on failure. Derived/computed numbers are rendered read-only —
  business math lives in the engine only, never in a client.

## 4. The card manifest
- Add an entry to `server/dashboards.json` (`id`, `label`, `subtitle`, `group`, `order`,
  `kind: "editable"|"viewonly"`, `url`, `color`). The app and `home.html` both render from
  it live — changing cards never requires rebuilding anything. `viewonly` cards are plain
  web views (good for surfacing read-only pages from other systems you run).
- The `url` must be reachable FROM THE SURFACE that loads it (phone/emulator/hub browser
  are different network vantage points — README quickstart step 0). After editing the
  manifest, force-stop + relaunch the app; it loads each dashboard page once per process.

## 5. Assistant surface (optional but recommended)
- Expose the engine CLI to your assistant (an MCP server that shells to it, or direct
  shell access). Give the assistant a standing instruction file for the domain, and start
  it with the pre-write rule: call the engine's `sync-status` before the first write of a
  session; if unresolved conflicts exist, decide each one immediately (newer real-world
  fact wins; merge when the two sides changed different fields; the phone wins ties —
  its author touched the data last), correct through normal engine calls, mark resolved,
  and notify the owner once with what was chosen. The protocol doc covers why this is safe.

## 6. Native phone editing (optional — build when phone editing matters)
A dashboard is fully usable without this step: the browser page (with its edit controls)
and your assistant cover viewing and editing from day one, and the phone still shows the
dashboard page as a card. Add native screens when you actually want offline phone editing
for the domain. When you do:
- In `app/`: a Room entity/DAO/repository/ViewModel/screen per table, modeled on the leads
  module (id-keyed) — name-keyed tables differ only in using the name as the outbox record
  key. Every local edit writes the entity table and the outbox in one transaction; the
  sync worker drains the outbox (drop on applied/rejected, retry on error) then pulls by
  cursor. Bump the Room DB version with a CREATE-only migration for new tables; a new
  dashboard database gets its own pull cursor.
- Build screens from the `ui/fields/` widget library (validated text, dates, select chips,
  checkbox, currency, read-only). Add screenshot-test previews for every new row/widget
  state, record goldens, and actually look at the rendered PNGs — a green diff only proves
  stability, not correctness.

## 7. Verify before you call it done
- Sync acceptance per table: push create lands with `updated_by='phone'` and regenerates
  the dashboard; replaying the same mutation id is a no-op; a stale `base_version` logs a
  conflict and still applies; the pull cursor returns the row; a tombstoned delete flows
  through pull; browser desktop-actions round-trip; invalid input returns 400 and writes
  nothing; pre-existing CLI output is byte-identical.
- Test with disposable rows and tombstone them when done. If you script UI checks on an
  emulator, remember its host loopback is `10.0.2.2`, not `localhost`.
